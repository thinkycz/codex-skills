# Explain current product capabilities

Use for client meetings, admin walkthroughs and practical instructions about an existing application. Confirm the audience, requested language and surfaces; reuse known scope rather than asking for facts available in the repository.

1. Map actual navigation, screens, roles, settings and relevant data flows from current source/documentation. When runtime access exists, inspect the intended deployment read-only and label any mismatch. An empty queue does not prove the feature is absent.
2. Explain what each section does, who uses it, and its relationship to mobile/web behavior. Distinguish a setting from a per-record snapshot, an enabled feature from a currently disabled prompt, and a stored event from delivered notification/device behavior.
3. For first-login/testing instructions, trace account creation or invitation, role selector, email field, password setup/recovery, expiry and shared access. Do not invent a default password or claim mail delivery from source code alone.
4. Return a concise section/function/user-facing effect/prerequisite-or-limitation table, or role-based steps for a requested test. Name observed labels accurately and mark unverified client/deployment behavior.
5. If a spreadsheet or document is requested, use the available artifact workflow and validate its contents and layout. A prose request alone does not require an export or an extra skill chain.

Inspect forms without submitting them. Client explanations do not authorize changing settings, approving records, creating accounts or messaging the client. Preserve uncertainty where current runtime evidence is unavailable.
