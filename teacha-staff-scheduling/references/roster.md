# Roster procedure

Use the current UI labels and available capabilities; recorded layouts can drift.

1. Confirm the account, branch and displayed month/year. Read existing shifts and availability requests for the requested dates. Resolve ambiguous employee identities before editing.
2. Build the intended changes from current user decisions, including exact start/end times. Check branch opening hours or presets when relevant, but do not convert a previously used time into a permanent policy. Expand recurring instructions into concrete dates in the requested period.
3. Approve a request through its approval flow when available. Requests may permit adjusted times; verify the resulting assignment rather than assuming approval copied every field.
4. Before adding, search for an exact existing assignment and overlapping assignments, including other branches if the interface exposes them. Leave an exact match alone. For a conflict, use the user's explicit replacement/overlap instruction or surface the unresolved choice; do not silently override it.
5. When replacing, identify the specific old assignment and use the supported replacement/edit flow. Preserve other workers and dates. If the UI needs separate delete/create steps, establish the exact replacement first and verify both outcomes; report partial failure rather than recreating repeatedly.
6. After an uncertain save or timeout, reload and inspect the assignment before retrying. Verify branch, date, employee, times and request status for each item. A success toast alone is insufficient.
7. Change a month request lock only when requested; inspect its persisted state after saving. Availability requests, assigned shifts and attendance/payroll are different records.

Use branch/date/employee/time/status in the final result, with screenshots when useful. Scheduling can trigger built-in application notifications; do not additionally message employees unless requested.
