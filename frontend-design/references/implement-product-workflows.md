# Product workflow acceptance

Translate the confirmed direction into the daily tasks users perform. A product-wide redesign should improve hierarchy, navigation and scanability as well as appearance. Keep a narrow correction narrow; do not turn every spacing fix into a redesign.

- Choose layouts that fit the feature: a calendar for dates, checklist or board for tasks, persistent composer/history for chat, and purposeful readers/editors for documents. Reuse existing capabilities and components rather than inventing unsupported workflows or presenting everything as the same CRUD table.
- Make the current location and next action clear. Group navigation logically, remove accidental duplicate links, and keep authorized tools reachable. Hide advanced controls progressively without making core actions hard to find. Preserve requested direct access when simplifying navigation.
- Standardize shared buttons, input geometry, icon alignment, menus, panels and contrast through established tokens. Audit shared consumers after component changes; fix accidental inconsistency without forcing every feature into the same layout.
- Apply warm, playful, pastel or rounded styling only when confirmed for this project. Keep text/code surfaces readable and semantics such as errors or overdue payments clear. Do not transplant one project's colors, radii or navigation decisions into another.
- Preserve routes, permissions, persisted data, integration contracts and supported locales. Verify translated feature content, validation, empty states and guided instructions as well as shell labels; a translated toolbar does not prove the page is localized.
- Inspect real populated, empty, loading and error states at the relevant desktop/mobile widths and themes. Use isolated representative data. Seed a shared or operational database only within explicit scope; do not make the app look populated by changing unrelated data.

Report workflow and rendered evidence proportionally to the request, including any pages or states still unverified. A successful build alone does not establish improved usability.

Respect an explicit light-only or dark-only product contract across portals, dialogs, shared components, native controls and system-preference changes. Verify foreground and background colors together in actual overlays; do not add a theme toggle or dark-mode variant to a light-only app as part of a contrast fix. A theme rule applies to that product, not every project.
